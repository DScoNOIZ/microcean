Архитектура: пять слоёв сборки

Система разделена на слои по степени «интеллектуальности» решений. Тяжёлые универсальные модели привлекаются только там, где без них не обойтись; основная работа выполняется лёгкими специализированными компонентами.

СлойОтветственностьМеханизмы
Координация (верхний) Приём задачи на естественном языке; разбиение на под-задачи; разрешение конфликтов между фрагментами; общая координация сборки. Модель высокого уровня; вызывается точечно, а не для каждой операции.
Рой микро-сетей (средний) Верификация контрактов фрагментов, генерация интерфейсов, оценка пригодности. Множество малых специализированных сетей; активация по типу задачи (sparse MoE — «разреженная смесь экспертов»: активна лишь сеть, подходящая к задаче).
Эволюционный отбор Подбор комбинаций фрагментов: мутация, скрещивание, отбор по функции пригодности. GA (генетический алгоритм) / GP (генетическое программирование) над подмножествами фрагментов; fitness («приспособленность») = ошибка + вес + конфликты; схема-теорема Холланда как теоретический фундамент.
P2P-инфраструктура Поиск фрагментов, распространение обновлений, синхронизация состояния без центрального сервера. Kademlia DHT (распределённая хеш-таблица: общая «адресная книга» сети без главного сервера) — поиск за O(log n); push-pull gossip (соседи обмениваются новостями, как слухами) — рассылка за O(log n); CRDT (структуры данных, сходящиеся к общему виду сами) — сходимость реплик; rarest-first («сначала редкое») — репликация редких фрагментов.
Доверие Консенсус и репутация без энергозатратных вычислений. PBFT (консенсус на случай лжи участников, 3f+1) для совета координаторов; Raft (консенсус для честных участников, 2f+1) внутри доверенного кластера; hashgraph aBFT как DAG-вариант; репутация = исполняемые тесты + Sybil-защита (защита от толпы фальшивых личин, Douceur, 2002).

Рабочий цикл сборки

  1. Постановка задачи. Пользователь или агент формулирует требование высокоуровнево: «собери поисковый движок по документам с векторным индексом».
  2. Декомпозиция. Планировщик разбивает требование на классы под-задач: парсинг, хранение, поиск, сетевой протокол, шифрование.
  3. Поиск кандидатов. DHT-запросы находят фрагменты каждого класса: токенизаторы, индексы, TLS-обёртки, шифрование с проверкой подлинности (AEAD).
  4. Эволюционный подбор. Генетический алгоритм перебирает комбинации, отбраковывает несовместимые интерфейсы, развивает жизнеспособные варианты.
  5. Верификация роем. Микро-сети проверяют каждый фрагмент на соответствие контрактам; несоответствующие отбрасываются.
  6. Разрешение конфликтов. Верхний уровень улаживает споры между фрагментами и чинит интеграции.
  7. Финальная сборка и тестирование. Полный прогон тестового набора на собранной программе.
  8. Возврат в сеть. Удачная сборка публикуется обратно как фрагмент — экосистема пополняется.

Путь к прототипу

Первый практический эмбрион уже существует в миниатюре: нужные функции уже сейчас вручную «вытягиваются» из модулей вместо подключения пакета целиком — так работает одна из практик повторного использования кода. Цель проекта — автоматизировать такое извлечение и сделать его децентрализованным: сочетание этих двух свойств и есть минимальный работающий прототип Microcean. Автоматизация — заявленная цель; сроки не обещаются.
